# 维护、迁移与故障排查

## 与已有部署共存

这个仓库不是当前服务器代理服务的安装目录。当前服务器原有的
`mihomo.service` / `~/.config/mihomo-managed/` 没有迁移到本仓库。
新工具使用 `mihomo-server.service` 和 `~/.config/mihomo-server/`。
默认端口相同，因此当前代理运行时直接安装会因端口冲突退出。

若需在同一台机器试用，应选择四个不同的空闲端口。source 新的 shell.sh
会在当前 shell 定义新的 proxy 函数；不要同时把两个项目的 shell.sh 加入
同一个启动文件。仓库创建过程没有安装新版本到真实 HOME，也没有修改
现有服务或 shell 启动文件。

## 路径

| 内容 | 默认位置 |
|---|---|
| 应用及隔离 Python 环境 | `~/.local/share/mihomo-server/` |
| 独立管理命令 | `~/.local/bin/mihomo-server` |
| 私有配置、节点、订阅 | `~/.config/mihomo-server/` |
| 历史节点 | 私有目录中的 `backups/` |
| 更新状态 | 私有目录中的 `state/` |
| systemd 用户单元 | `~/.config/systemd/user/mihomo-server*` |

支持 `XDG_CONFIG_HOME`。可通过安装前的 `MIHOMO_SERVER_CONFIG` 指定
私有目录；安装器生成的命令会记住该路径。应用位置固定在当前用户
`~/.local/share/mihomo-server/`，每个用户只支持一套本工具的安装。

机器私有数据不会写入仓库；`.gitignore` 只是额外防护，不能代替秘密检查。
`settings.json` 内的 `subscription_url` 使用编辑器填写，或安装时通过隐藏
提示/私有 URL 文件读取，避免进入 shell 历史和进程参数。

## 变更与升级

安装器拒绝覆盖已有应用、配置、命令和同名服务，不提供未经验证的原地升级。
升级操作建议安排短维护窗口：

1. 在私有目录外另存一份私有备份，不放进 Git。
2. 用原版本仓库执行卸载；配置默认保留。
3. 将保留的旧私有目录移到你选定的备份位置，核对应用目录是否已移除。
4. 用新版本安装，使用旧 `nodes.yaml` 导入节点、从私有文件提供订阅 URL。
5. 验证 `proxy doctor`、订阅更新和重启，再处理旧备份。

卸载仅删除安装清单记录且指纹匹配的文件；用户修改过的应用文件和未记录
文件会保留，所以可能需要你检查后处理残留目录。控制命令或 systemd 单元
被修改时，卸载直接拒绝，避免误停其他服务。卸载保留的私有数据属于有意
保存的恢复材料，不会自动清除。

编辑主配置后，`proxy restart` 会先执行 Mihomo 语法校验，再重启服务。
若需调整端口，要同时修改 shell.sh 内的代理地址；建议重新安装以统一生成。
改变可选服务需要同步规则、组和 settings.json 中的 services。

## 更新与回退

更新忽略订阅中的规则、DNS、控制器设置，只导入节点。保留已有节点优先级，
清理以订阅状态/联系方式开头的标签。支持的节点协议在 manager.py 中明确
列出，Mihomo 的 `-t` 负责最终配置校验。首次导入也会执行 `-t`。

默认每六小时刷新，systemd 执行失败后十五分钟重试。手动 `proxy update`
失败会返回非零状态并保留可用配置，手动调用自身不会启动后台重试任务。
没有订阅来源时静态节点仍可用；安装激活不会为这种情况开启更新定时器。

下载上限 8 MiB、40 秒超时，健康扫描最多等待 150 秒。很大的订阅或大量
慢节点可能超过扫描预算；这种情况会拒绝更新而不牺牲现有配置。暂不支持
必须额外设置 Authorization 头的订阅源，也不包含订阅转换服务。

若应用新 provider 后测试失败，会恢复原节点文件并刷新原 provider，必要时
重启专用服务。自动保存最近八个节点版本。需要手动恢复某个备份时，可先
复制当前节点到私有备份，再把选定版本复制到 nodes.yaml，并运行 proxy
restart 和 proxy test。文件 provider 会观察文件变化，所以操作时应先停止
更新定时器/正在执行的更新服务，避免竞争；不要在终端打印节点文件。

## 诊断边界

- `proxy status` 显示的是实际运行模式和自动组选择；启动后部分检查可能
  尚未完成，界面会显示 checks still running。
- `proxy doctor` 区分 curl 的 DNS、连接、超时、TLS 错误，以及已完成传输后
  的 HTTP 认证/限制响应；它不自动改全局 DNS、防火墙或 SSH。
- 本地上游 DNS 检查使用系统 resolver；目标 DNS、隧道和 HTTPS 由实际
  请求/原生健康检查验证，不通过修改系统 resolver 解决问题。
- OpenAI 401 和 W&B 根路径 404 是预期传输结果，不代表登录、付费、模型
  权限、账号地域政策或 SDK 请求均被验证。
- OpenAI API 可用不保证 ChatGPT/Codex 的所有域名都适用；服务策略变化时
  需要按实际业务调整检查目标。所有公共检查端点都可能临时故障。
- 固定优先级 fallback 不按延迟频繁切换，但高优先级节点恢复时会切回；
  不提供多轮迟滞或无损迁移 TCP 会话。
- 订阅中的上游 TLS 选项会保留，包括可能已有的 skip-cert-verify；用户应
  自行评估订阅可信度。目标 HTTPS 探测不会使用 curl --insecure。

## 初版验证记录（2026-10-29）

- 15 项测试（含两个真实 Mihomo 校验回归用例）全部通过，覆盖：订阅下载/解析失败、重复节点、候选验证失败、应用失败
  回退、成功更新保留备份及权限、HTTP 与 TLS 分类、端口冲突、安装拒绝
  覆盖、卸载保留私有数据、保护修改后的 unit、shell on/off。
- 在临时 HOME 中执行真实 Python venv + PyYAML 安装，使用已安装的
  Mihomo v1.19.25 校验生成配置，并执行完整卸载。应用树被删除，私有
  节点保留。临时 HOME 在测试结束后清理。
- 仓库验证使用合成节点，不复制或发布本机真实订阅。不在真实用户管理器
  中启用新服务，不对本机旧服务执行故障注入。
- 已验证无效 Mihomo 配置会使安装失败，并清理本次创建的应用与私有配置。
- 校验会额外把文件 provider 节点交给 Mihomo 解析，防止单独 -t 未初始化
  文件 provider 时漏过无效协议。
- 本仓库通用安装器的 --activate 分支仍需在目标机器用其真实节点完成
  端到端验证；初始网络检查失败会阻止激活。核心原生 failover 机制来自
  之前服务器部署中已验证的方案，但不将该结果当作其他服务器的保证。
